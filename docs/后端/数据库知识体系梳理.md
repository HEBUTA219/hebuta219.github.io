# 数据库知识体系梳理

## 一、基础核心知识

本模块包括“什么是数据库、数据如何结构化存储、核心要素有哪些”，是后续所有知识的基础。

### 1. 数据库本质与分类

数据库（Database）是按照特定数据结构组织、存储和管理数据的仓库，核心价值是实现数据的高效存储、查询、维护与共享，避免数据冗余与不一致。按数据存储模式与关联特性，分为两大核心类别：

| 类别                    | 核心定义                                       | 存储结构                   | 核心特性                                 | 代表产品                                                     | 适用场景                                                     |
| :---------------------- | :--------------------------------------------- | :------------------------- | :--------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 关系型数据库（RDBMS）   | 基于关系模型（二维表）的数据库，数据间关联紧密 | 二维表（行=记录，列=字段） | 支持事务ACID、复杂关联查询、数据一致性强 | MySQL、Oracle、SQL Server、PostgreSQL                        | 企业级应用、管理系统（如科研管理、电商、ERP）                |
| 非关系型数据库（NoSQL） | 不依赖关系模型，适用于非结构化/半结构化数据    | 键值对、文档、列族、图结构 | 高并发、海量数据存储、灵活扩展，弱事务   | MongoDB（文档）、Redis（键值）、Elasticsearch（检索）、Neo4j（图） | 高并发场景（如直播、社交）、非结构化数据存储（如日志、附件） |

**核心选型原则**：数据关联紧密、事务要求高→关系型数据库（优先MySQL，开源易用；企业级高端场景可选Oracle）；高并发、海量非结构化数据→非关系型数据库（如缓存用Redis，文档存储用MongoDB）。

### 2. 数据库核心概念

所有概念均直接对应实操中的库、表、数据操作，需精准理解并记忆：

- **数据库（Database）**：数据库的最高层级容器，用于隔离不同业务的数据。
- **表（Table）**：存储特定业务数据的二维结构，对应现实中的“实体”（如竞赛成果表、学生表），每张表有唯一名称，包含多个字段与多条记录。
- **字段（Column）**：表的列，对应实体的“属性”（如竞赛名称、学生学号），每个字段有固定数据类型、约束规则。
- **记录（Row）**：表的行，对应实体的“实例”（如一条竞赛成果记录、一条学生信息记录），每条记录有唯一标识（主键）。
- **主键（PK，Primary Key）**：表的唯一标识字段，特性：非空（NOT NULL）、唯一（UNIQUE）、一般不可更新，一张表仅能有一个主键（可复合主键）。实操中常用自增大整数（BIGINT AUTO_INCREMENT），无业务含义（避免业务变更导致主键失效）。
- **外键（FK，Foreign Key）**：用于关联两张表的字段，指向另一张表的主键，核心作用是保障数据参照完整性（外键值必须是参照表主键的有效值或NULL），实现表间数据联动。
- **域（Domain）**：字段的取值范围，落地为“数据类型+约束规则”（如竞赛级别域：{国家级、省级、校级}）。
- **模式（Schema）**：数据库对象（表、视图、索引等）的集合，MySQL中Schema与Database等价，用于对象隔离与权限管理。
- **事务（Transaction）**：一组不可分割的数据库操作，要么全成功，要么全失败，核心保障数据一致性（如新增竞赛成果+关联学生数据）。

### 3. 字段数据类型与约束规则

字段设计直接影响存储效率、查询性能与数据有效性，需结合业务场景精准选择，以下为关系型数据库（MySQL）核心类型与约束：

#### （1）核心数据类型

| 类型分类   | 具体类型                        | 适用场景                                                     | 设计原则                                          |
| :--------- | :------------------------------ | :----------------------------------------------------------- | :------------------------------------------------ |
| 整数类型   | TINYINT、SMALLINT、INT、BIGINT  | 状态、计数、主键、外键（BIGINT适配海量数据）                 | 按需选择，避免大类型浪费空间（如状态用TINYINT）   |
| 字符串类型 | CHAR、VARCHAR、TEXT             | CHAR（固定长度，如学号）、VARCHAR（可变长度，如名称）、TEXT（长文本，如备注） | VARCHAR长度按需设置，长文本优先用TEXT             |
| 时间类型   | DATE、TIME、DATETIME、TIMESTAMP | DATE（日期）、TIME（时间）、DATETIME（日期时间，无时区）、TIMESTAMP（时间戳，有时间区） | 常规场景用DATETIME，需自动记录时间用TIMESTAMP     |
| 小数类型   | DECIMAL(p,s)、FLOAT、DOUBLE     | DECIMAL（精度高，如金额、绩点）、FLOAT/DOUBLE（精度要求低的场景） | 精度要求高的场景必须用DECIMAL，避免浮点数精度丢失 |

#### （2）核心约束规则

- **主键约束（PRIMARY KEY）**：非空+唯一，表的唯一标识，实操中建议用自增主键。
- **外键约束（FOREIGN KEY）**：参照另一张表的主键，保障表间数据关联一致性，可配置级联操作（ON DELETE CASCADE/ON UPDATE CASCADE）。
- **非空约束（NOT NULL）**：字段值不可为NULL，用于必填字段（如竞赛名称、学生学号）。
- **唯一约束（UNIQUE）**：字段值唯一（可多个NULL），用于唯一标识字段（如专利申请号、手机号）。
- **默认约束（DEFAULT）**：字段未赋值时使用默认值（如状态字段DEFAULT 0），减少业务代码判断。
- **检查约束（CHECK）**：限制字段取值范围。

### 4. 数据库三大范式

范式（Normal Form）是关系型数据库表结构设计的规范，核心目标是减少数据冗余、提升数据一致性，实操中严格遵循前三大范式（第四、五范式适用于超复杂场景）：

- **第一范式（1NF）**：字段不可再分（原子性），即每个字段的值必须是不可拆分的最小单位（如“学生信息”拆分为姓名、学号、专业，而非整体存储）。
- **第二范式（2NF）**：在1NF基础上，非主键字段必须完全依赖主键（消除部分依赖），即主键为复合主键时，非主键字段不能仅依赖复合主键的某一部分（实操中建议用单一主键，天然满足2NF）。
- **第三范式（3NF）**：在2NF基础上，非主键字段不能传递依赖于主键（消除传递依赖），即非主键字段不能依赖其他非主键字段（如所有人员信息统一存储在用户表，其他表仅通过外键关联，不重复存储姓名、学号）。

**范式与反范式平衡**：核心表严格遵循三大范式（减少冗余）；高频查询场景可适当反范式（冗余字段，如论文成员表冗余“作者姓名”，减少关联查询次数），但需确保冗余字段同步更新，避免数据不一致。

## 二、核心应用知识

本模块包括“如何将业务场景转化为数据库设计、如何操作数据”的问题，涵盖ER图设计、SQL语句（DDL/DML/DQL/TCL/DCL）、表关联设计三大核心内容，是数据库实操的核心。

### 1. ER图设计

ER图（实体-关系图）是将业务场景可视化、标准化的工具，核心要素为“实体、属性、关系”，用于梳理业务逻辑并指导表结构设计。

#### （1）ER图核心要素

- **实体（Entity）**：现实中需存储数据的独立业务对象（如竞赛成果、学生、教学活动），ER图中用“矩形”表示，对应数据库中的“表”。
- **属性（Attribute）**：实体的特征或描述信息（如竞赛名称、学生绩点），ER图中用“椭圆”表示，对应表中的“字段”，需标注主键（下划线标注）。
- **关系（Relationship）**：实体间的关联关系，ER图中用“菱形”表示，核心分为三大关系，是表关联设计的核心依据。

#### （2）实体三大关系

| 关系类型      | 核心判定逻辑                                           | 表关联落地规则                                               |
| :------------ | :----------------------------------------------------- | :----------------------------------------------------------- |
| 一对多（1:N） | 一个A实体可对应多个B实体，一个B实体仅能对应一个A实体   | 在“多”的一方建外键，指向“一”的一方主键，外键加NOT NULL约束，核心业务表配置级联操作 |
| 一对一（1:1） | 一个A实体仅能对应一个B实体，一个B实体仅能对应一个A实体 | 在附属实体/字段较多的一方建外键，指向主实体主键，外键加UNIQUE约束 |
| 多对多（N:M） | 一个A实体可对应多个B实体，一个B实体可对应多个A实体     | 必须建中间关联表，中间表含两个外键（分别指向A、B实体主键），可加自身主键与业务字段 |

#### （3）ER图设计标准化流程

1. 业务梳理：明确核心业务流程、参与对象、数据存储需求，提取实体与属性，排除非存储对象（如审核步骤，用状态字段记录）。
2. 实体与属性定义：为每个实体分配唯一名称，明确核心属性（必填/可选），标注主键。
3. 关系判定：结合业务场景，判断实体间关系类型（1:N/1:1/N:M），标注关系含义。
4. 优化调整：复用基础实体（如人员信息统一关联用户表）、消除冗余关系、调整布局提升可读性。
5. 落地转化：将实体转化为表、属性转化为字段、关系转化为外键，生成建表SQL。

### 2. SQL语句全梳理

SQL（结构化查询语言）是操作数据库的标准语言，按功能分为五大类：DDL（数据定义语言）、DML（数据操纵语言）、DQL（数据查询语言）、TCL（事务控制语言）、DCL（数据控制语言），需熟练掌握并灵活运用。

#### （1）DDL（数据定义语言）—— 表结构创建与维护

核心作用：创建、修改、删除数据库对象（库、表、索引、约束等），核心语句：CREATE、ALTER、DROP、TRUNCATE。

```sql
-- 1. 创建数据库（IF NOT EXISTS：避免数据库已存在时报错）
CREATE DATABASE IF NOT EXISTS research_management_platform 
DEFAULT CHARSET utf8mb4 -- 字符集：支持中文，避免乱码
DEFAULT COLLATE utf8mb4_general_ci; -- 排序规则：默认

-- 2. 使用数据库（操作表前必须先指定用哪个库）
USE research_management_platform;

-- 3. 创建表（IF NOT EXISTS：避免表已存在时报错；ENGINE=InnoDB：支持事务和外键）
CREATE TABLE IF NOT EXISTS t_competition_collection (
    c_id BIGINT AUTO_INCREMENT COMMENT '主键ID（自增）', -- 自增主键
    competition_name VARCHAR(100) NOT NULL COMMENT '竞赛名称（必填）', -- 非空约束
    competition_level VARCHAR(50) NOT NULL COMMENT '竞赛级别（国家级/省级/校级）', -- 非空
    award_level VARCHAR(50) NOT NULL COMMENT '获奖等级', -- 非空
    award_time DATETIME COMMENT '获奖时间（可空）',
    status TINYINT DEFAULT 0 COMMENT '状态：0-未审核/1-已通过/2-驳回', -- 默认约束
    create_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间（自动填充）',
    update_time DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间（自动更新）',
    remark TEXT COMMENT '备注（长文本，可空）',
    -- 约束配置
    PRIMARY KEY (c_id), -- 主键约束
    CHECK (competition_level IN ('国家级', '省级', '校级')), -- 检查约束（限制级别取值）
    -- 索引配置（提升查询速度，高频查询字段建索引）
    INDEX idx_competition_level (competition_level), -- 普通索引
    INDEX idx_award_time (award_time) -- 普通索引
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT '竞赛成果主表'; -- 引擎+字符集+表注释

-- 4. 修改表结构（3个常用操作：新增字段、修改字段、删除字段）
-- 4.1 新增字段（主办单位）
ALTER TABLE t_competition_collection 
ADD COLUMN organizer VARCHAR(100) COMMENT '主办单位'; -- 新增字段，可空

-- 4.2 修改字段（获奖等级长度从50改为60，支持“特等奖”等更长名称）
ALTER TABLE t_competition_collection 
MODIFY COLUMN award_level VARCHAR(60) NOT NULL COMMENT '获奖等级（含特等奖）'; -- 修改类型/长度/约束

-- 4.3 删除字段（删除主办单位字段，谨慎！删除后字段数据丢失）
ALTER TABLE t_competition_collection 
DROP COLUMN organizer;

-- 5. 删除表（IF EXISTS：避免表不存在时报错；谨慎使用！数据不可恢复）
DROP TABLE IF EXISTS t_competition_collection;

-- 6. 清空表数据（保留表结构，数据不可恢复；比DELETE快，因为不记录日志）
TRUNCATE TABLE t_competition_collection;
```

#### （2）DML（数据操纵语言）—— 数据增删改

核心作用：对表中数据进行新增、修改、删除，核心语句：INSERT、UPDATE、DELETE，需结合事务保障数据一致性。

```sql
-- 1. 新增数据（单条+批量）
-- 单条新增
INSERT INTO t_competition_collection (
    competition_name, competition_level, award_level, award_time, status
) VALUES (
    '全国大学生数学建模竞赛', '国家级', '一等奖', '2025-11-01', 1
);

-- 批量新增（高效）
INSERT INTO t_competition_collection (
    competition_name, competition_level, award_level, award_time, status
) VALUES 
('全国大学生英语竞赛', '国家级', '二等奖', '2025-10-20', 1),
('省级大学生计算机竞赛', '省级', '一等奖', '2025-09-15', 1);

-- 2. 修改数据（必须加WHERE，精准定位）
UPDATE t_competition_collection 
SET award_level = '特等奖', update_time = CURRENT_TIMESTAMP 
WHERE c_id = 1; -- 按主键修改，避免批量错误

-- 3. 删除数据（必须加WHERE，核心表建议配合级联操作）
DELETE FROM t_competition_collection 
WHERE c_id = 1; -- 按主键删除
```

#### （3）DQL（数据查询语言）—— 数据查询

核心作用：从表中查询所需数据，核心语句：SELECT，需熟练掌握多表关联、筛选、排序、分页、分组统计，是工作中最常用的SQL。

```sql
-- 1. 单表查询（筛选+排序+分页）
SELECT 
    c_id, competition_name, competition_level, award_level, award_time, status
FROM t_competition_collection
WHERE status = 1 -- 筛选已通过数据
  AND competition_level = '国家级' -- 多条件筛选
ORDER BY award_time DESC -- 按获奖时间降序
LIMIT 0, 10; -- 分页（第1页，每页10条，起始索引=（页码-1）*每页条数）

-- 2. 多表关联查询（LEFT JOIN/INNER JOIN，核心场景）
-- 关联竞赛成果表与参赛学生表，查询成果详情+学生信息
SELECT 
    cc.c_id AS competition_id,
    cc.competition_name,
    cc.award_level,
    cs.student_id,
    u.c_name AS student_name -- 关联用户表获取姓名
FROM t_competition_collection cc
LEFT JOIN t_competition_student cs 
    ON cc.c_id = cs.competition_id
LEFT JOIN t_user u 
    ON cs.student_id = u.c_id
WHERE cc.c_id = 1
ORDER BY cs.sort ASC;

-- 3. 分组统计查询（GROUP BY+聚合函数）
SELECT 
    competition_level, -- 分组字段
    COUNT(c_id) AS award_count, -- 统计数量
    MAX(award_time) AS latest_award_time -- 最新时间
FROM t_competition_collection
WHERE status = 1
GROUP BY competition_level -- 按级别分组
HAVING award_count > 5 -- 过滤分组结果（仅统计数量>5的级别）
ORDER BY award_count DESC;

-- 4. 子查询（IN/NOT IN，复杂查询场景）
SELECT c_name AS student_name 
FROM t_user
WHERE c_id IN (
    SELECT student_id 
    FROM t_competition_student
    WHERE competition_id IN (
        SELECT c_id 
        FROM t_competition_collection
        WHERE competition_level = '国家级' AND award_level = '一等奖'
    )
);
```

#### （4）TCL（事务控制语言）—— 数据一致性保障

核心作用：控制事务的提交与回滚，保障多步操作的一致性，核心语句：START TRANSACTION、COMMIT、ROLLBACK、SAVEPOINT，仅InnoDB引擎支持。

```
-- 开启事务
START TRANSACTION;

-- 步骤1：新增竞赛（不指定c_id，靠自增生成）
INSERT INTO t_competition_collection (
    competition_name, competition_level, award_level, award_time, status
) VALUES (
    '全国大学生电子设计竞赛', '国家级', '一等奖', '2025-12-01', 1
);

-- 获取刚新增竞赛的自增ID（关键：避免写死ID）
SET @competition_id = LAST_INSERT_ID();

-- 步骤2：用获取到的ID关联学生
INSERT INTO t_competition_student (competition_id, student_id, role, sort)
VALUES (@competition_id, 1001, '队长', 1), (@competition_id, 1002, '成员', 2);

-- 提交事务
COMMIT;
-- 出错则回滚：ROLLBACK;
```

**事务ACID特性**：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability），是事务的核心保障。

#### （5）DCL（数据控制语言）—— 权限管理

核心作用：管理数据库用户与权限，保障数据安全，核心语句：CREATE USER、GRANT、REVOKE、DROP USER，遵循“最小权限原则”。

```
-- 1. 创建用户（指定访问主机，localhost仅本地，%允许远程）
CREATE USER IF NOT EXISTS 'research_admin'@'localhost' IDENTIFIED BY 'Admin@123456';
CREATE USER IF NOT EXISTS 'research_dev'@'%' IDENTIFIED BY 'Dev@123456';

-- 2. 授予权限（数据库级、表级、字段级按需分配）
-- 管理员：授予数据库所有权限（本地访问）
GRANT ALL PRIVILEGES ON research_management_platform.* TO 'research_admin'@'localhost';
-- 开发人员：授予查询、新增、修改权限（无删除权限）
GRANT SELECT, INSERT, UPDATE ON research_management_platform.* TO 'research_dev'@'%';
-- 报表人员：仅授予查询权限
GRANT SELECT ON research_management_platform.* TO 'research_report'@'%';

-- 3. 刷新权限（立即生效）
FLUSH PRIVILEGES;

-- 4. 回收权限
REVOKE UPDATE ON research_management_platform.* FROM 'research_report'@'%';

-- 5. 删除用户
DROP USER IF EXISTS 'research_dev'@'%';
```

## 三、优化知识

本模块核心解决“如何让数据库运行更高效、更安全、更易维护”的问题，涵盖索引优化、查询优化、事务优化、备份恢复、监控告警五大核心内容。

### 1. 索引优化

索引是基于B+树结构的快速数据定位工具，核心作用是减少数据库扫描行数，提升查询速度，但索引会降低增删改效率（需维护索引结构），因此需精准设计。

#### （1）索引核心类型与适用场景

| 索引类型                | 核心特点                                   | 适用场景                                         | 创建语法                                                  |
| :---------------------- | :----------------------------------------- | :----------------------------------------------- | :-------------------------------------------------------- |
| 普通索引（INDEX）       | 最常用，无唯一性约束                       | 高频查询、筛选、排序字段（如竞赛级别、获奖时间） | CREATE INDEX idx_name ON 表名(字段名);                    |
| 主键索引（PRIMARY KEY） | 默认创建，非空+唯一，查询效率最高          | 表的主键字段（如c_id）                           | 创建表时指定PRIMARY KEY (字段名);                         |
| 唯一索引（UNIQUE）      | 字段值唯一，可含NULL，兼顾唯一性与查询效率 | 唯一标识字段（如专利申请号、手机号）             | CREATE UNIQUE INDEX idx_name ON 表名(字段名);             |
| 复合索引（多字段组合）  | 多字段组合索引，遵循“最左前缀原则”         | 多字段联合查询（如竞赛级别+状态筛选）            | CREATE INDEX idx_name ON 表名(字段1, 字段2);              |
| 外键索引（FOREIGN KEY） | 外键字段创建，提升关联查询效率             | 所有外键字段（如competition_id）                 | 创建表时指定FOREIGN KEY 字段名 REFERENCES 关联表(字段名); |

#### （2）索引设计核心原则

- 高频查询、筛选、排序字段建索引，低频查询字段不建索引；
- 长文本字段（如TEXT）、NULL值较多的字段不建索引；
- 复合索引遵循“最左前缀原则”，查询时需包含复合索引的第一个字段；
- 避免过度索引（一张表索引数量建议≤5个），定期删除冗余索引；
- 用EXPLAIN分析查询语句，判断索引是否生效（type字段非ALL，key字段不为NULL）。

### 2. 查询优化

通过优化SQL语句与查询逻辑，减少数据库扫描行数与资源占用，核心优化技巧如下：

- 避免SELECT *，仅查询所需字段（减少数据传输量与扫描行数）；

- 多表关联优先用LEFT JOIN，避免子查询嵌套过深（嵌套≤3层，复杂查询用关联替代）；

- WHERE条件精准筛选，优先用主键、索引字段作为筛选条件，避免用OR（可用UNION替代）、NOT IN（可用LEFT JOIN+IS NULL替代）；

- 分页查询优化：大数据量分页（如第1000页）用主键定位替代LIMIT（`WHERE c_id > 9990 LIMIT 10`）；

- 避免在索引字段上做函数运算（如`DATE(award_time) = '2025-11-01'`，会导致索引失效）；

- 用EXPLAIN分析执行计划，定位低效查询（如全表扫描、索引失效），针对性优化。

  #### 分页优化：

  ```
  SELECT 字段列表 
  FROM 表名
  [WHERE 筛选条件]
  [ORDER BY 排序字段 排序方式]
  LIMIT 起始索引, 每页条数;
  
  -- 例子
  SELECT c_id, competition_name, award_level, award_time
  FROM t_competition_collection
  WHERE status = 1 AND competition_level = '国家级'
  ORDER BY award_time DESC
  LIMIT 20, 10; -- 第3页：(3-1)*10=20
  ```

  - 起始索引：从第几条数据开始查询（索引从 `0` 开始计算）
  - 每页条数：每页展示的记录数量
  - 核心公式：`起始索引 = (页码 - 1) × 每页条数`

  - 第 1 页：`LIMIT 0, 10`
  - 第 2 页：`LIMIT 10, 10`
  - 第 N 页：`LIMIT (N-1)*10, 10`

  #####  关键注意事项

  1. **必须搭配 `ORDER BY`**

     分页前必须先排序，否则每次查询的结果顺序可能不一致，导致分页数据重复或遗漏（比如第 1 页和第 2 页出现同一条记录）。

  2. **索引优化**

     排序字段（如 `award_time`）建议建立索引，否则数据量大时，排序操作会非常耗时，影响分页查询效率。

  3. **不同数据库的语法差异**

     - MySQL/MariaDB：用 `LIMIT 起始索引, 条数`
     - PostgreSQL：用 `LIMIT 条数 OFFSET 起始索引`
     - SQL Server：用 `OFFSET 起始索引 ROWS FETCH NEXT 条数 ROWS ONLY`

  4. **避免大索引分页**

     当起始索引很大时（比如 `LIMIT 10000, 10`），查询效率会下降，可通过**主键分页**优化：

     ```
     -- 假设上一页最后一条记录的c_id是10000
     SELECT c_id, competition_name, award_time
     FROM t_competition_collection
     WHERE status = 1 AND c_id > 10000
     ORDER BY c_id ASC
     LIMIT 10;
     ```

### 3. 事务优化

事务并发执行时，需平衡性能与一致性，避免死锁与并发问题（脏读、不可重复读、幻读），核心优化技巧：

- 控制事务粒度：尽量缩小事务范围，避免长事务（长事务占用锁资源，导致并发阻塞）；
- 合理设置隔离级别：MySQL默认REPEATABLE READ，兼顾一致性与性能，无需修改（隔离级别从低到高：READ UNCOMMITTED→READ COMMITTED→REPEATABLE READ→SERIALIZABLE）；
- 避免死锁：统一事务内表操作顺序（如先操作主表，再操作子表）、避免长时间持有锁（事务内尽快提交/回滚）；
- 检测与解决死锁：用`SHOW ENGINE INNODB STATUS;`查看死锁日志，定位死锁语句并优化。

### 4. 备份与恢复

数据是核心资产，需定期备份，避免数据丢失（误删除、数据库崩溃、服务器故障），核心覆盖备份策略与恢复方法：

#### （1）备份类型与策略

- 全量备份：备份整个数据库，适合定期全量（如每天凌晨1点），用mysqldump工具：        

  `mysqldump -u 用户名 -p 数据库名 > /backup/全量备份文件名_$(date +%Y%m%d).sql`

- 增量备份：备份自上次全量/增量备份以来变更的数据，适合数据量大场景（如每6小时增量）；

- 日志备份：开启MySQL二进制日志（binlog），支持基于时间点恢复，需在my.cnf中配置：        `log_bin=ON ``log_bin_basename=/var/lib/mysql/mysql-bin ``server_id=1`

- 备份存储：备份文件存储到异地服务器或云存储，避免本地故障导致备份文件丢失；

- 恢复测试：每周定期测试备份文件的恢复可用性，确保备份有效。

#### （2）数据恢复案例

```bash
-- 1. 全量备份恢复
mysql -u 用户名 -p 数据库名 < /backup/全量备份文件名_20251201.sql

-- 2. 基于binlog时间点恢复（恢复到2025-12-01 09:30:00前的数据）
mysqlbinlog --start-datetime="2025-12-01 00:00:00" --stop-datetime="2025-12-01 09:30:00" /var/lib/mysql/mysql-bin.000001 | mysql -u 用户名 -p
```

### 5. 监控与告警

实时监控数据库运行状态，及时发现并解决问题，核心覆盖监控指标、工具与告警配置：

- **核心监控指标**：CPU占用率、内存使用率、磁盘空间、连接数（max_connections）、慢查询数量、事务提交/回滚率、锁等待时间；
- **核心监控工具**：        
  - MySQL自带工具：SHOW STATUS（运行状态）、SHOW VARIABLES（配置）、slow_query_log（慢查询日志）；
  - 第三方工具：Prometheus+Grafana（可视化监控+告警）、Zabbix（全方位监控+邮件/短信告警）、Navicat（可视化管理+简单监控）。
- **告警配置**：设置关键指标阈值（如CPU>80%、慢查询>10条/分钟、连接数>80%max_connections），触发阈值后发送告警（邮件/企业微信/短信），及时排查问题。
